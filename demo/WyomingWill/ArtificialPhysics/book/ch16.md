## Entry 16.1 — Baseline physicomimetics update and the split-Newtonian variant with mass exponent (§16.3.1, PDF pp. 540–541)

**Particle update:**
- Δx = vΔt.
- Δv = FΔt/m.
- v_next = (v + Δv)·c_f, with friction coefficient c_f ∈ [0, 1].

**Force law (Eq. 16.1):** a split Newtonian with exponents p_m on mass and p_d on distance.
- F_ij = −G (m_i m_j)^p_m / r^p_d for r ∈ [0, D) (repulsive).
- F_ij = +G (m_i m_j)^p_m / r^p_d for r ∈ [D, D_max] (attractive).
- F_ij = 0 for r > D_max.
- There is **no Fmax** in this form.
- Per-particle parameters: m, c_f. Per-interaction parameters: G, D_max, D, p_m, p_d.
- **No numeric values are given.**

**BPP conversion:**
- The existing Ch. 3 Newtonian code generalizes trivially: add p_m and per-type mass, and make D_max explicit.
- Note: the repulsive branch is negative here, the opposite of Ch. 14's LJ sign convention.

## Entry 16.2 — Differentiated particle types: rings of arbitrary radius (§16.3.2, PDF pp. 541–542)

**Claim:** two particle types, one light and one heavy, are enough to make **ring formations of arbitrary radius**. The level of heterogeneity is set by the number of types and their ratio.
- No parameters are given.
- This is the "heavy centre, light ring" idea that appears elsewhere in the book: ring radius is set by the mass ratio through (m_i m_j)^p_m.

**BPP conversion:**
- Easy particle demo: one heavy particle and N light ones, with the light–light and light–heavy laws differing in D (or in the mass term).
- ★ **3D:** the same construction gives a **spherical shell** around a heavy centre. With drones this is a shell or "dome" around a point of interest.
- The porter must choose the masses and D. A good check is ring radius against mass ratio.

## Entry 16.3 — Virtual particles (§16.3.3, PDF p. 542)

**Concept:** particles with no physical counterpart that inject state or knowledge. Examples:
- a lead point ahead of a tracked object;
- points along the intruder–resource line (Entry 16.6);
- a blind-spot point (Entry 16.8);
- field centroids (Entry 16.7);
- the virtual particles used in Ch. 11 uniform coverage.

**BPP conversion:** groundwork. Agents need a list of non-body "virtual" sources with a type tag. Easy. It is reused by Entries 16.6–16.8 and by the existing coverage port.

## Entry 16.4 — Differentiated and asymmetric interaction types (§16.3.4, PDF pp. 542–543)

- Each (type u → type v) pair can have its own force law and parameters. The effect can be asymmetric (A affects B differently from how B affects A), which deliberately breaks Newton's third law.
- **Examples:**
  - Ch. 3 square lattices, where same-spin and different-spin particles have different D;
  - Ch. 14 obstacle avoidance (robot–robot, robot–obstacle and robot–goal laws).

**BPP conversion:** groundwork. Use a force-law lookup table keyed by (sourceType, targetType). The current BPP AP code probably has hard-coded classes, so refactor it into this table. Easy, and it is the enabling step for everything heterogeneous (Ch. 3 square lattice, Ch. 14, Ch. 17 quarks, the protector examples here).

## Entry 16.5 — Graph-based interaction design: digraphs, index variables, wildcards, scalability (§16.5.1–16.5.4, PDF pp. 547–550)

**Interaction model:**
- Each node is a particle type.
- A directed edge (u, v, F_uv) means type u exerts a force F_uv on type v.
- Self-loops and cycles are allowed; a missing edge means no interaction.

**Notation:**
- A type family U = {u1, u2, …}.
- **Index variables** u_j stand for per-type, distinct laws (design modularity).
- **Wildcards** u_* mean the same law and parameters for every member (behaviour modularity, shared laws).
- When it is ambiguous, the more specific reading applies.

**Figures:**
- Fig. 16.4: a two-type full graph.
- Fig. 16.5: the profile for u_j, which is affected by v, w and x.
- Fig. 16.6: a u_j self-loop (a distinct law for each type) plus u_* → u_* (one shared law between different u types).

**Scalability:** that profile adds exactly one new law per added type, so parameters grow linearly rather than quadratically as they would with all pairs.

**BPP conversion:** this is a design and config format, not a simulation.
- Implement the force-law table (Entry 16.4) with wildcard fallback: look up the (u_j, v_k) entry, then fall back to (u_*, v_k), then (u_*, v_*).
- Optional: draw the interaction graph in the GUI. Easy.

## Entry 16.6 — Example problem: centralized resource protection (§16.4.1, §16.5.5.1, Figs. 16.1, 16.7, PDF pp. 543–545, 550–552)

**Task:**
- A fixed resource sits at the centre of a circular defence perimeter.
- **Intruders** (one type, slightly faster than the protectors) appear just outside the perimeter after a short random wait and head for the resource, avoiding protectors.
- An intruder is removed if it is destroyed, hits the resource, or is chased out of the perimeter, and is then respawned.
- **Two objectives that conflict:**
  - the mean per-step incursion depth of intruders inside the perimeter;
  - the ratio of resource hits to intruder runs.

**Interaction model (Fig. 16.7):**
- Protector family P = {p1…pn}.
- Virtual intruder-point family I = {i'1…i'm}: points along the intruder→resource line at a set fraction. i'1 (fraction 1.0) is the intruder itself.
- The resource r → p_j.
- Exactly one i'_k → p_j per protector type.
- A p_j self-loop (each type has its own formation law).
- p_* → p_* (one shared law for avoiding protectors of other types).
- Parameters scale linearly in |I| or |P|.

**Concrete solution from [263]:**
- **9 protectors of 2 types**: **3 on an inner ring** guarding against hits and **6 on an outer ring** reducing incursion.
- One intruder type, I = {i}.
- Hand-coded solutions with this modular design **beat optimization methods** that lacked the modular design.
- **No numbers are given in this chapter** (speeds, radii, laws, scores).

**Unit tests (§16.6.4 / 16.5.6, PDF p. 553):**
- Test the outer-ring type alone with an incursion-distance measure, scaling its team size.
- Test the inner-ring type alone with the hit ratio over a fixed-time simulation, scaling its team size.
- This is the process used to build the hand-coded solutions in [263].

**BPP conversion:**
- First as a 2D particle sim. It needs:
  - an intruder agent with a scripted pursue-and-avoid controller;
  - capture, hit and escape rules;
  - respawn;
  - the two metrics.
- Medium.
- **Porter must decide:** all numeric values (perimeter radius, ring radii, speeds, capture radius). These are only in [263].
- ★ **3D:** drones defending a point, with an inner shell and an outer shell. The VIP variant (§16.6.3, PDF p. 556) moves the resource independently, for example a ground vehicle escorted by drones, which tests the "uncontrolled collaborating agent" challenge.
- This is a new entry for the plan.

## Entry 16.7 — Example problem: multi-field surveillance (§16.4.2, §16.5.5.2, Figs. 16.2, 16.8, PDF pp. 545–546, 552)

**Task:**
- Fixed objects are scattered in several "fields", each with a simple geometric distribution unknown to the monitors.
- Monitors with a surveillance radius must spread out to cover as many objects as possible across all fields.
- Fig. 16.2 shows two fields.

**Interaction model (Fig. 16.8):**
- Monitor family M = {m1…mn}.
- Centroid virtual-particle family C = {c1…cn}, one per field, with an upper bound on the number of fields assumed.
- c_j → m_j, one-to-one.
- An m_j self-loop.
- Objects o → m_* and m_* → m_*.
- Monitors cannot tell which field an object belongs to.
- Parameters scale linearly with |M|.

**No experiment or numbers are given.**

**BPP conversion:**
- 2D particle demo of two fields (for example a line and a disk of objects) and two monitor types, each attracted to its field centroid and lattice-spreading over it. Measure the fraction of objects within surveillance range.
- Medium; all values are porter-chosen.
- ★ **3D/drones:** monitors at altitude over several ground "fields". This ties to the APO-from-altitude idea (Ch. 18–19) and to coverage.

## Entry 16.8 — Example problem: covert tracking (§16.4.3, §16.5.5.3, Figs. 16.3, 16.9, PDF pp. 546, 552–553)

**Task:**
- Targets ("mice") random-walk.
- Trackers ("cats") try to stay as close as possible without being detected.
- Each target has a field-of-view cone with a blind spot behind it. Fig. 16.3 shows a gray vision sector.
- **Two objectives:** minimize distance, and avoid detection.

**Interaction model (Fig. 16.9):**
- A virtual blind-spot point m'_j (an offset behind a target of type j) → c_j (the tracker type assigned to that target type).
- A c_j self-loop.
- m'_* → c_* (the same reaction to all other targets and trackers).
- No tracker formation is needed.

**Details are in [58, 181]**, which are not reproduced here.

**BPP conversion:**
- Easy to medium particle demo: a random-walk target with heading, a vision cone, a virtual point behind it, and a tracker attracted to it and repelled from the cone.
- Metrics: mean distance and detection count.
- ★ **3D:** a drone shadowing a ground vehicle or another drone from its blind spot. A cone is a natural 3D generalization.
- The cone angle, range and offset are porter-chosen.

## Entry 16.9 — Prediction vs control dilemma: test metrics under actuation constraints (§16.6, esp. §16.6.4, PDF pp. 554–557)

**Three sources of model–vehicle mismatch (§16.6.3):**
1. Explicit Euler integration of what are really ODEs. It is unstable for large Δt and inaccurate in general.
2. Actuation constraints: turning radius, maximum velocity, maximum acceleration, obstacles that physically block. The force law only *suggests* motion.
3. Uncontrolled dynamic collaborators, such as humans or a moving VIP.

**Study summarized (from [58]):** a lattice swarm under a varied **maximum angular velocity** constraint. Three test measures:
- **Settling time:** the time from random initial conditions until the mean scalar acceleration drops below a threshold. The threshold value is not given.
- **Lattice quality:**
  - compute the Delaunay triangulation of the settled particles;
  - keep the subset of nodes within **80% of the swarm's maximum radius** from its centroid;
  - report the **coefficient of variation of edge lengths** in that subset.
- **Suggested position difference:** the Euclidean distance between the position predicted by the particle model and the actual position after the control system. It is tracked during an optimization (learning) of parameters.

**Results (qualitative only):**
- Lattice quality is not substantially damaged until the constraint is very large.
- **Settling time is shorter** with the constraint, because the constraint removes energy.
- More constraint → larger suggested-position difference, but the learner compensated.

**Suggested but not implemented:** run Runge–Kutta in parallel with Euler, as a test only, to expose integration error in chosen test cases.

**BPP conversion: high value, and directly relevant to the existing drone work.**
- BPP already has this exact split: AP computes a 5 Hz "suggested" waypoint, and the PX4-style quadcopter "actualizes" it. The suggested position difference is literally |AP waypoint − drone position|.
- Log it per drone, alongside settling time and Delaunay edge-length CV. That gives a quantitative way to compare Newtonian (jitters) with LJ (settles), and with/without the Ch. 13 friction fix.
- Delaunay in 2D is easy (Bowyer–Watson in Lua). For 3D lattices, use tetrahedral Delaunay, or simply the CV of nearest-neighbour distances as a cheaper proxy.
- ★ **Angular-velocity constraint test:** apply it to a ground-robot or fixed-wing model (turn-rate limit) in BPP. A fixed-wing "dumbbell" has exactly this constraint.
- ★ **Euler vs RK4 shadow integrator:** run AP's particle update with both and log the divergence. Cheap.
- Effort: easy to medium. Recommended as **groundwork done early**, since it gives the metrics for Ch. 13's friction work.
